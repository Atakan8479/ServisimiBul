# Architecture decision register — approved vs unresolved

Approval state is important: never turn a proposal into a settled decision without developer confirmation.

## APPROVED decisions
| ID | Decision | Rationale/consequence |
|---|---|---|
| D001 | Java 21 source/bytecode compatibility; JDK 25 developer toolchain; Spring Boot; Maven; React + TypeScript; PostgreSQL via Supabase; modular monolith | Existing backend is the base. JDK 25 may run Maven and IntelliJ, but Maven must continue compiling with Java 21 compatibility. |
| D002 | Flyway owns schema migrations; Hibernate `ddl-auto=validate` | Avoid manual database drift. |
| D003 | Supabase provides PostgreSQL, NOT Supabase Auth | Spring Security is responsible for identity. |
| D004 | Server-side sessions + HttpOnly cookie, NOT JWT | CSRF protection and secure session lifecycle needed. Spring Session JDBC is recommended, still inspect compatibility. |
| D005 | Email verification must precede login | Account enabled/suspension state is separate from email verification. |
| D006 | Same province coverage allowed across districts | Validate school province equals coverage neighborhood province. |
| D007 | Admin CRUD and bulk CSV import were originally approved for the school catalog | Superseded for pilot sequencing by D019; retained here as decision history. |
| D008 | Operator automatically appears once ALL publication requirements are satisfied | Derive visibility at query time; no second manual public approval. |
| D009 | Operator business name and public contact phone REQUIRED | Contact phone shown on public operator profile; no contact-publish-toggle field. Can hide entire public profile. |
| D010 | Admin refusal of correctable operator application sends operator to editing/resubmission path | Reasons/audit retained; correction is not permanent ban. |
| D011 | ServiceOffering optional; each offering has independent neighborhood coverage | OfferingCoverage must be subset of OperatorSchoolCoverage. |
| D012 | UKOME official distance price bands as JSON, updated from admin panel | No UKOME PostgreSQL fare tables. Persistent writable storage required. |
| D013 | Price model C: MVP shows official UKOME tariff only; operator-specific prices deferred | Do not add `monthly_price` to MVP ServiceOffering, do not assign exact distance using neighborhood alone. |
| D014 | Costs monitored manually initially; Supabase Free preferred for development | Do not opt into paid plan without approval. |
| D015 | Parents anonymous; students have no personal records | Preserve zero-account public discovery. |
| D016 | Secure bootstrap for two ADMIN accounts | Public registration creates OPERATOR only. |
| D017 | Adopt Flyway through a controlled drop and recreation of the four existing empty geography tables | Read-only inspection on 2026-10-12 verified `province`, `district`, `neighborhood`, and `school` have zero rows and no Flyway or Supabase migration history. Destructive execution still requires a separately reviewed plan and explicit approval. |
| D018 | Gate 2 schema/security contract: V1 retains `province.created_at`, reproduces the inspected geography schema, keeps RLS enabled, removes `anon`/`authenticated` table and sequence access (including Flyway-owner defaults), and leaves `service_role` unchanged | `postgres` is used only for controlled migrations/administration. A separately provisioned `servisimibul_app` login receives only explicit object grants and table-scoped backend RLS policies; it is not a Data API role and does not receive `BYPASSRLS`. Approved 2026-10-12. |
| D019 | Pilot school catalog is curated manually through admin CRUD and initially contains only schools the team is actively testing with | Do not scrape, synchronize, bulk import, or attempt to preload all Istanbul schools now. Bulk CSV import is deferred, not permanently rejected, and requires a new explicit decision before implementation. Approved 2026-10-12. |
| D020 | Public registration accepts email, password, business name, and contact phone; it creates only an `OPERATOR` in `DRAFT` | Email verification is required before login. Registration, resend, and password-recovery responses must not reveal whether an account exists. Passwords are 12–64 characters and at most 72 UTF-8 bytes, without composition rules. Approved 2026-10-13. |
| D021 | Verification and password-reset links are finalized by a frontend GET page that POSTs the token to the API | Verification tokens are hashed, single-use, expire after 24 hours, and a resend invalidates earlier tokens. Resend has a 60-second cooldown and limits of 5/account/hour and 20/IP/hour. Password-reset tokens are hashed, single-use, expire after 30 minutes, and a successful reset revokes every session. Approved 2026-10-13. |
| D022 | Spring Session JDBC stores server-side sessions; production frontend and `/api/v1` are same-origin | Normal login uses a 30-minute inactivity session. “Remember me” is optional and gives a persistent session with a non-sliding 90-day absolute lifetime. At most two sessions may exist per account; a third login removes the oldest. Password/primary-email changes, password reset, account disablement, suspension, or role change revoke all sessions. Approved 2026-10-13. |
| D023 | Session cookie contract: `SBSESSION`, HttpOnly, `SameSite=Lax`, path `/`, and no `Domain` attribute | `Secure=true` everywhere except explicit local HTTP development. CSRF applies to every state-changing browser request, including authentication endpoints. No JWT or browser token storage. Approved 2026-10-13. |
| D024 | Operator application states are `DRAFT`, `PENDING`, `CHANGES_REQUESTED`, and `APPROVED`; suspension is separate | Verified operators may use a limited dashboard. Submit/resubmit moves to `PENDING`; correction requests require a reason. There is no permanent `REJECTED` state in MVP. Approved operators' validated profile edits take effect immediately without renewed admin approval; moderation/re-review may be reconsidered later. Approved 2026-10-13. |
| D025 | Two admins are created only through an explicitly enabled, one-shot backend bootstrap command | It reads temporary environment credentials, is unavailable over HTTP, requires exactly two admin identities, never logs secrets, and does not change existing admin passwords on rerun. Approved 2026-10-13. |
| D026 | APIs use RFC Problem Details plus stable application error codes; pagination is zero-based with default size 20 and maximum size 50 | Validation may include field errors; sensitive details are omitted. Use 400/401/403/404/409/429 consistently and `Retry-After` for explicit rate-limit responses. Results require stable ordering. Approved 2026-10-13. |
| D027 | Public contact email is excluded from MVP | Mandatory public contact phone is the sole public contact channel. Authentication email remains private. Approved 2026-10-13. |
| D028 | New operator profiles default `is_publicly_visible` to `true` | This does not bypass publication rules: the operator appears only when every derived publication condition is satisfied. The operator may hide the profile at any time. Approved 2026-10-13. |
| D029 | The identity table is named `app_user` | Avoids PostgreSQL `user` keyword ambiguity while retaining the approved `AppUser` domain name. Approved 2026-10-13. |
| D030 | Operator application review decisions are exactly `APPROVED` and `CHANGES_REQUESTED` for MVP | Suspension remains a separate account/profile condition and is not a review decision. Approved 2026-10-13. |
| D031 | Vehicle and ServiceOffering remain optional for discovery, but every ServiceOffering must reference an active Vehicle owned by the same operator | `vehicle_id` is mandatory. An offering draft may have zero coverage, while publication requires at least one valid ServiceOfferingCoverage entry that belongs to the same OperatorSchool and is a subset of its general coverage. Approved 2026-10-14. |
| D032 | Vehicle plate and capacity are mandatory; vehicle removal is lifecycle-based rather than hard deletion | Canonical plate values are trimmed, uppercased, stripped of spaces/hyphens, and globally unique. Capacity must be greater than zero; nullable `available_seats`, when present, is between zero and capacity. Deactivation transactionally unpublishes dependent offerings; reactivation never republishes them automatically. Approved 2026-10-14. |
| D033 | Admin-editable tariff JSON is stored in a backend-only persistent filesystem directory configured by `SB_TARIFF_STORAGE_DIR` | The directory must be mounted on a persistent deployment volume and is never the packaged JAR, classpath, frontend, or PostgreSQL fare tables. Supabase Storage is intentionally excluded for MVP because its S3 compatibility does not provide object versioning and its server-side access keys have broad bucket access. Approved 2026-10-14. |
| D034 | Tariff updates use immutable version files plus atomic replacement of `current.json`, with optimistic concurrency | Each write supplies the expected current version; stale updates return 409 instead of last-write-wins. Temp-file and atomic move occur on the same filesystem. Rollback creates a new version containing prior content; history is never overwritten. MVP permits one tariff-writer backend instance; horizontal write scaling requires a new distributed-lock/store decision. A-09 owns off-volume backup and restoration verification. Approved 2026-10-14. |
| D035 | Official tariff bands and provenance have a strict JSON contract | Bands are sorted, contiguous, non-overlapping half-open intervals `[minDistanceKm,maxDistanceKm)`; the first starts at zero and only the final band has `maxDistanceKm=null`. Amounts are nonnegative integer kuruş. Source title, official URL, authority, academic year, effective dates, and version are mandatory. Approved 2026-10-14. |
| D036 | The frontend baseline is a Node.js 24 LTS/npm Vite React+TypeScript SPA | Commit `package-lock.json`; use strict TypeScript, ESLint, Prettier, React Router Data Mode, React Hook Form with Zod, Vitest, React Testing Library, and MSW. Production uses same-origin relative `/api/v1`; local Vite proxies `/api` to Spring Boot so cookies and CSRF retain same-origin behavior. Browser-visible `VITE_*` variables must contain no secrets. Approved 2026-10-14. |
| D037 | Operator business name is optional; public contact phone remains required | Supersedes the business-name requirement in D009 and the business-name portion of D020. Registration may omit `businessName`; missing, explicit `null`, or blank input is stored as `NULL`. A supplied name is trimmed and must contain 2–120 characters. Profile PATCH may clear it. Public and authenticated response DTOs expose nullable `businessName`. Approved 2026-10-15. |
| D038 | Operator approval is controlled centrally by `app.operator-approval.required=${OPERATOR_APPROVAL_REQUIRED:true}` | The safe default preserves D024. The Istanbul pilot must explicitly set the variable to `false`, which bypasses application-state restrictions without changing stored statuses or bypassing verification, enablement, suspension, ownership, coverage, offering, or visibility rules. Approval-specific writes then return 409 `approval_workflow_disabled`; moderation and suspension remain available. Approved 2026-10-17. |
| D039 | Approval-required permissions are state-specific | `DRAFT` may edit and submit, `PENDING` is application-read-only, `CHANGES_REQUESTED` may edit and resubmit, and `APPROVED` has full operator resource management. Disabled or suspended operators have no operator-management access. Approved 2026-10-17. |
| D040 | Initial production uses one Spring Boot backend instance | The provider must supply automatic recovery, health probes, monitoring/alerting, controlled migrations, durable tariff storage, and rollback. Horizontal scaling is deferred until measured load or availability needs justify it; the design must retain Spring Session JDBC and document shared rate limiting, tariff writes, connection budgets, migration coordination, and singleton jobs. Approved 2026-10-17. |
| D041 | B-10 uses bounded configurable in-memory rate limiting for the single-instance pilot | Preserve the established authentication limits, add endpoint-specific verification/reset/search policies, hash sensitive identities, use actual network peers by default, and never evict active authentication protection on saturation. State resets on restart and is not shared between instances. Distributed or edge enforcement requires a new deployment-topology decision. Approved 2026-10-17. |
| D042 | Railway, Render, and a managed VPS remain deployment candidates; no provider is selected | Deployment code and documentation stay provider-neutral. Cloud creation, deployment, provider-specific proxy trust, and paid-plan selection require human approval. Approved 2026-10-17. |
| D043 | Registration explicitly discloses the public visibility of an eligible operator profile and its contact phone | D028 remains in force: new profiles default to publicly visible, but publication still requires every existing eligibility condition. No separate acknowledgement or publication-confirmation step is required. Operators may disable profile visibility later. This product decision is not a complete legal or KVKK compliance assessment; independent legal review remains separate. Approved 2026-10-17. |
| D044 | The combined local development launcher temporarily bypasses email delivery by auto-verifying newly registered test accounts | D005 remains the production rule and the safe default. The bypass is explicit, local-only, creates no verification token or email, does not rewrite existing accounts, and production startup must reject disabled verification. Remove the launcher override when live email verification testing begins. Approved 2026-10-18. |
| D045 | Windows development and full-stack verification use a disposable loopback PostgreSQL 17 cluster instead of the shared Supabase database | `dev.ps1` never reads the ignored backend `.env`. It generates isolated admin/runtime passwords, applies Flyway in a one-shot process, starts the web application only as `servisimibul_app`, removes privileged and inherited credential variables, binds the stack to `127.0.0.1`, and deletes temporary state on exit. Direct runtime, migration, and ADMIN-bootstrap environment examples remain separate. Approved for A-12 implementation 2026-10-19. |
| D046 | Persistent shared-data development is an explicit separate mode, never the default isolated launcher | `dev-supabase.ps1` loads only the ignored runtime `.env`, requires the restricted `servisimibul_app` role and a non-loopback TLS JDBC URL, disables Flyway and ADMIN bootstrap, binds the applications to loopback, and warns that application writes persist in shared Supabase. `dev.ps1` and automated tests remain disposable and must never use Supabase. Approved 2026-10-20. |
| D047 | Parent accounts use the `PARENT` role while public discovery remains anonymous | REQ-01 introduces no public parent registration and no demand data. A synthetic verified parent may be created only by the local-profile bootstrap after both an explicit disposable flag and the isolated-database marker are verified. It receives no operator or admin authority. Approved through GitHub issue #84 and implementation approval, 2026-10-20. |
| D048 | Transport demand identity and participation are backend-authoritative | A demand is unique for school + pickup neighborhood + server-configured academic year, including closed or archived rows. Creation adds only the creator's ACTIVE support; a duplicate returns the existing demand without adding the caller. Supports retain one row per parent, use ACTIVE/WITHDRAWN lifecycle, require morning and/or afternoon plus at least one approved reason, and derive public counts only from active supports belonging to enabled, verified PARENT accounts. Anonymous reads remain available; mutations require a PARENT session and CSRF. Approved through GitHub issue #85 and implementation approval, 2026-10-20. |
| D049 | Demand-specific operator responses publish immediately from current eligibility, with stable identity and immutable publication versions | Keep one response row per demand + operator with ACTIVE/WITHDRAWN lifecycle. An eligible operator may publish without response-specific admin approval; repeated POST while ACTIVE is idempotent, while a true initial publication or reactivation increments the version and appends one immutable publication event. Public display is derived at read time from the OPEN demand and the complete current operator/school/exact-neighborhood eligibility predicate, including the effective D038 approval policy; loss of eligibility hides rather than deletes history. Vehicle and ServiceOffering data are never required. Morning/afternoon directions are operator declarations, not verified capacity, price, route, or service guarantees. Approved through GitHub issue #88 and implementation approval, 2026-10-21. |
| D050 | Demand comments are public plain text with deliberately small baseline moderation | Only an ACTIVE supporting parent or eligible operator may post on an OPEN demand. Parents display only as `Veli`; an operator's name/profile link appears only when the existing public-discovery predicate matches that demand, otherwise it displays as `Servis işletmecisi`. Bodies are trimmed to 2–1000 characters. The same author/demand/body is blocked for 10 minutes and posting is limited to 5 attempts/account/10 minutes. Authors may hard-delete only their own comments. Baseline persistence supports `PUBLISHED` and `HIDDEN`; admin hide/unhide audit belongs to REQ-08. Replies, editing, media, AI moderation, private chat, phone/address detection, and general comment approval are deferred. Approved for GitHub issue #87, 2026-10-21. |
| D051 | Each real demand-service publication creates a distinct parent feedback opportunity for every eligible supporting parent, without automatically closing the demand | Feedback is unique by support + immutable publication event. Opening the feedback screen starts configurable 7-day reminder and 14-day expiry deadlines; an unopened opportunity expires 45 days after publication. Explicit “satisfied” moves the support to `SATISFIED`; explicit “not satisfied” restores it to `ACTIVE`; unattended expiry moves it to `INACTIVE_EXPIRED`. Support statuses are `ACTIVE`, `AWAITING_FEEDBACK`, `SATISFIED`, `INACTIVE_EXPIRED`, and `WITHDRAWN`; AWAITING_FEEDBACK remains participating for aggregates and D050 comment eligibility. A demand closes only when no eligible ACTIVE/AWAITING support remains, recording `FULFILLED` only when at least one parent explicitly satisfied and otherwise `INACTIVE`; administrative closure remains distinct. Inactive demands may reopen through same-row support reactivation. A single-instance idempotent scheduler is sufficient for the pilot and sends no email/push. Approved through GitHub issue #89 and implementation approval, 2026-10-22. |
